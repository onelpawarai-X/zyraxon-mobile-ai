## Session ŌĆö background-video lag (commit ed411d3) + typing proof (42ac643)

Real cause of "everything lags / background crawls": the gt/ clips were VP8/VP9
webm. Browsers almost never hardware-decode VP9, so every frame was CPU-decoded.
nightlights.webm was 3840x2160, city.webm 1920x1080. Re-encoded to H.264 Main /
yuv420p, capped 1280x720 -> measured 50-60% less page CPU on city/rain/nebula.

MEASUREMENT LESSONS (these cost the most time):
- Do not trust a single "fps" number. Use requestVideoFrameCallback presented
  frames + Performance.getMetrics TaskDuration (page CPU seconds). A/B the SAME
  file in the SAME headless session; headless software rasterisation is far worse
  than any real phone, so absolute numbers mean nothing without a baseline.
- The landscape bg/*.mp4 clips were ALREADY H.264 720p. Re-encoding them was a
  pure loss (generation loss, 0.6-0.8x dropped-frame ratio). git checkout them.
  Lesson: only re-encode what is actually mis-encoded.
- nightlights is a 3 fps NASA timelapse. "11 fps" was NOT a bug; my threshold was.
  Never upsample a timelapse, and judge stalls relative to the clip's OWN frame
  interval, not a 24 fps yardstick. Same trap twice: a wrong budget, not a bug.
- scripts/optimize-media.sh: keep nightlights at fps=3 (was 12 = pointless upscale).

test/mediaperf.mjs enforces MAX_EDGE 1280 / MIN_KEEP 0.6 / MIN_FPS 2 / MAX_STALL 6x.
CPU is reported but NOT enforced (whole-page task time, too noisy). Verified the
test actually catches the originals: old 4K nightlights fails on >1280px.
Pass a src as argv to check a new clip before committing it.

Desktop main.cjs: the unconditional app.disableHardwareAcceleration() was itself
costing frames; now opt-in via ZYRAXON_FORCE_SOFTWARE=1.

METHODOLOGY LESSON (cost several wrong conclusions):
A single perf sample under this container's software rasteriser is NOT evidence.

of >=5 samples, and prove a guard fails on an injected regression before trusting
